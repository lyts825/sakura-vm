# 项目常驻服务的运行归属

项目设置的 `services` 继续支持依赖顺序、环境、就绪检查和自动健康检查。启动的每个服务现在有独立、持久的 cgroup v2，普通 `setsid`、双重 fork 和脱离 tmux 的后台子进程仍属于该次运行。常驻服务不使用短任务的有限时限；就绪和健康检查仍使用 [短任务清理](guest-task-cleanup.md)。

首次启动会用固定、无项目环境的准备命令检查 Python 3 与 tmux，缺失时通过发行版官方包管理器安装。实际启动还要求可写 cgroup v2、`cgroup.kill` 和 Linux pidfd；不具备这些条件时在项目代码与环境执行前拒绝，不回退到仅清理进程组。

## 启动、停止与恢复

控制服务先保存本次运行意图，客户机再准备专属 cgroup 和根用户归属文件。tmux pane 的固定启动器先进入该域，发布 PID、创建时间和完整 pane 身份，再等待提交。控制服务保存完整归属后才允许项目代码运行；失去提交的 pane 会退出，不继续执行项目代码。

停止核对同一客户机运行、boot ID、随机 run ID、cgroup inode、tmux session/pane 标识、PID 和创建时间，再通过已核对的 cgroup 清理整个运行，并确认域已空、已释放。清理用独立控制连接重试三次；全部失败时返回 `SERVICE_CLEANUP_FAILED`，保留归属，不把操作报告为成功。成功停止的记录仍保留供回执丢失后的幂等重试，不保存项目密钥或命令环境。

服务面板分别显示运行中、主进程已退出待清理、启动未确认、状态未确认和旧服务待迁移。主 pane 退出后，所属后台子进程仍需要显式停止；启动或停止未确认时继续保留原记录。对应 Job 保留具体错误码，错误和日志遮盖已知项目密钥，清理失败后可从面板重试。

修改服务命令、环境、密钥、运行时、目录或网络，以及移除服务前，必须先确认旧运行已经停止。暂停的实例仅接受已确认停止的服务记录；无法检查旧归属时拒绝覆盖。实际运行视图和配置保护使用同一归属，避免删除服务定义后无法再清理遗留进程。

启动准备、pane 创建、提交或就绪检查失败时只回滚本次新启动的服务，已在运行的依赖继续保留。客户机重启、运行记录替换或 pane 身份变化会拒绝使用旧记录终止新进程。健康检查任务隔离失败，或自动重启中服务归属、停止未确认，会暂停受影响服务的自动检查与重启；失败的手动操作保持暂停，成功的手动操作才恢复对应服务意图。

## 旧会话与边界

升级前已有的 `sakura-service-*` tmux 会话没有完整运行归属，返回 `SERVICE_SCOPE_UNMANAGED`。先保存工作并由管理员检查、停止旧服务及其实际后台子进程，再从项目入口重新启动。仅有会话名、工作目录或命令参数不能证明后台进程属于该项目，升级不会据此猜测并终止它们。

这管理 Sakura 启动的普通服务进程。项目主命令 `project.command` 仍走原有 tmux 路径，尚未迁移到此持久服务范围。客户机管理员和能自行迁移 cgroup 的特权代码不在此进程归属的保证范围内，项目网络模式也不因此覆盖普通系统 SSH、自行启动的进程或未知扩展。

单元回归位于 `tests/project-services-scope.test.ts`、`tests/workspaces-service-scope.test.ts` 与 `tests/development.test.ts`。真实发行版清理、回执丢失、替换身份及配置保护验证使用 `scripts/smoke-project-services-scope.ts`，具体证据见 [本轮实现记录](capability-completion.md)。
