# Linux 图形桌面验证

桌面使用 KDE Plasma，运行在内置 Alpine 3.23.4 x86_64 镜像以及 Debian / Ubuntu 的 systemd 适配中。Alpine 在 TigerVNC 的 X11 画布中运行嵌套 KWin/Wayland；Debian / Ubuntu 使用发行版提供的 Plasma 会话入口。桌面组件保存在实例磁盘上，使用独立的 `sakura-desktop` 普通用户；浏览器通过 noVNC 操作。不是其他 Linux 桌面发行版的镜像导入功能。

## 连接与生命周期

- 首次安装由用户在「桌面」标签触发，需要至少 1 GiB 内存，建议 2 GiB；软件包从发行版官方仓库下载。
- OpenRC 管理 Xvnc 和 KDE Plasma 会话，服务名为 `sakura-desktop`，随客户机启动。退出网页只关闭图形连接。
- 「外观与布局」可以保存 KDE Plasma 的每块逻辑屏幕分辨率（1280×800 至 1920×1080）、单屏/左右双屏/上下双屏布局、缩放（100% 至 200%）、主题、壁纸、强调色、面板位置、自动隐藏和动画偏好。双屏在同一个 VNC 画布内由 Xvnc RandR 划分；浏览器会按整体画布缩放，但不自动改变客户机双屏几何。应用已有会话配置时会重启桌面服务，偏好写入 `/etc/sakura/desktop-preferences`，重启实例后仍会恢复。旧版桌面安装会在首次应用新版偏好时自动升级并安装 `xrandr`。真实 Alpine 已验证单屏、横向双屏、纵向双屏的 RandR 监视器报告，以及完整 KDE 桌面在双屏配置下成功启动。Debian/Ubuntu 的完整桌面启动尚未实测；双屏不等于跨宿主物理显示器的独立窗口。
- Xvnc 仅监听客户机回环地址的 5901 端口。浏览器请求沿用服务令牌、同源及 Host 校验。
- Alpine Tiny Cloud 默认使用 `AllowTcpForwarding no`，因此图形流经固定命令 `exec nc 127.0.0.1 5901` 的 SSH 二进制通道传输。端点不接受自定义主机、端口或命令，也不修改 sshd 转发策略。
- 同一实例的安装请求合并执行，保留最近 16 KiB 进度日志。安装超时、失败可重试，停机取消服务端等待；客户机安装命令自身也有限时和互斥锁。
- 图形通道断开后按 1、2、4、8、15 秒间隔重连，最多重试 5 次；连接稳定 30 秒后重置次数。RFB 握手等待最多 30 秒，认证失败不自动重试，离开桌面会取消所有定时器和连接。
- SSH 状态检查失败时暂停新的图形连接，继续检查客户机状态；恢复为 `ready` 后自动重新连接，即使断线前后桌面状态都为 `ready`、此前已用完重试次数。正常的状态轮询不会绕过重试上限，单独的状态检查失败也不会中断仍然可用的图形连接。「重新连接」同时触发新的状态检查。
- SSH 仅对建立 TCP 连接前的 `ECONNREFUSED` 做最多 3 次短暂重试，沿用原超时预算，支持取消，并校验实例启动代次；不重试认证错误，不重放 Linux 命令。
- QEMU 使用独立 `-netdev` / `-device` 参数显式配置网卡 `vectors=4`，客户机可使用 MSI-X。

## 2026-09-21 连接稳定性修复

修复前，在已启动的桌面实例上进行 6 路并发 SSH 传输，重复出现 `ECONNREFUSED`，随后单次连接仍可成功。这与 [libslirp 监听实现](https://raw.githubusercontent.com/qemu/libslirp/master/src/socket.c) 中较小的连接等待队列相符，但没有据此把所有历史断连归因于它。服务端现在只对这种尚未建立 TCP 连接的短暂错误进行有限重试。

既有图形通道回归覆盖了真实 QEMU 的 VNC 握手、重启、快照恢复、连接中断自动重连，以及客户机 MSI-X 检查；这些连接层检查与桌面环境无关。Alpine 3.23 的 KDE Plasma 首次联网安装、非 root 会话、偏好应用和重启恢复已通过真实 VM 验证；Debian / Ubuntu 的软件包组合仍应在目标发行版上单独验证。新的 `SAKURA_TEST_CONNECTIONS=1` 回归通过了 300 次 SSH 传输、6 个并发客户端；已安装桌面的实例额外连续通过 3 轮相同压力测试，共 900 次。

单元测试覆盖未响应的 RFB 握手、连续失败的重试上限、认证失败、快速断连的退避、稳定会话后重置计数、离开页面释放连接，以及 SSH 重试期间取消和实例重启。

## 2026-09-24 断线恢复回归

生命周期推演确认了一个恢复缺口：SSH 和 VNC 同时失联时，`DesktopPanel` 保留最后一次 `ready` 状态，图形连接可能耗尽 5 次重试；SSH 恢复后再次返回 `ready`，不会改变原先连接 effect 的依赖，导致桌面继续停留在重试耗尽状态。现在状态轮询单独通知连接控制器客户机是否可用，由控制器暂停和恢复重连。认证失败仍需人工处理，停机、切换实例和离开桌面会释放控制器，迟到的状态响应不能重新打开旧连接。

客户机探测还会以 3 秒超时检查 `:1` 的 X 服务，避免仅凭旧的 ready 文件与残留 Plasma 进程报告就绪。新安装脚本同时监督 VNC 与 Plasma 两个子进程，任一退出都会清除 ready 文件、释放另一个进程并以失败状态退出，让 OpenRC / systemd 重启完整会话。该监督脚本在安装时写入客户机，已有实例需重新安装桌面脚本才能采用；前端恢复与状态探测改进立即生效。

回归覆盖 SSH / VNC 两种断线顺序、5 分钟失联、重试耗尽后恢复、握手期间失联、认证失败、手动重连和销毁后的迟到通知；真实本地 WebSocket / TCP 测试检查同时断线后的隧道释放与重建；POSIX shell 测试执行 Alpine / Debian / Ubuntu 生成脚本，检查失效的 X 服务以及任一子进程死亡后的清理。这里验证的是故障注入与恢复逻辑，没有复现下述 WHPX 长时间失联，也没有据此确认其根因。

本次 `npm test` 共 208 项通过，无跳过；`npm run build`（TypeScript 检查与 Vite 生产构建）通过。

## 已知限制

此前本机 WHPX 测试中曾出现 SSH 与桌面同时长时间失联：TCP 可以连接但收不到 SSH 握手，串口中的网络配置及 SSH 监听仍正常，QMP 可以正常关机；重启客户机后恢复。本轮曾在原配置上完成 4 轮重启及快照流程和约 1.6 GiB 的图像传输，没有复现这一现象。它与本轮明确复现的短暂 `ECONNREFUSED` 不同，根因仍未确认；MSI-X 配置与自动重连属于稳定性改进，不能据此保证该历史故障已被消除。因此功能仍标记为实验性。

桌面已提供文本剪贴板互通和可选 Fcitx5 中文输入，不包含 GPU/3D 加速、声音转发或 WSLg 单应用窗口集成。TCG 使用软件模拟，桌面启动和操作会明显慢于硬件加速。

可用 `SAKURA_TEST_DESKTOP=1` 配合 `npm run test:vm` 重跑联网安装、SSH 通道的 VNC 握手、重启和快照验证；追加 `SAKURA_TEST_CONNECTIONS=1` 可验证并发传输。客户机日志为 `/var/log/sakura-desktop.log`。GUI 或 SSH 长时间无法恢复时，可停止并重新启动实例。
