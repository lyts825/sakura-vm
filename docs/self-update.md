# 独立运行包自更新

在**原安装目录**执行以下命令。新包必须由 `npm run release:prepare` 生成，并已复制到本机目录；检查 SHA-256 清单后才会安装依赖和执行候选代码。

```powershell
npm run update:check -- D:\path\to\new-package
npm run update:stage -- D:\path\to\new-package
# 上一条输出版本路径，如 versions/0123456789abcdef0123456789abcdef
npm run update:activate -- versions/0123456789abcdef0123456789abcdef
# 重启 Sakura；npm start 或托盘会从新版本启动
npm run update:status
```

`stage` 将发行包复制到独立版本目录，使用包的锁文件安装生产依赖，在临时数据目录和随机回环端口启动新服务，并检查 HTTP 健康状态。`activate` 只切换小型启动指针；已运行的旧服务继续运行到重启。启动器在新版本未能就绪时自动切回旧版本。需要主动回退时，在原安装目录运行 `npm run update:rollback`，随后重启服务。`versions/` 中的旧版本保留，不会被自动删除。

第 2 版发行清单将 `.sakura-witness` 也纳入 SHA-256 校验，并要求包含 `ha-witness.js` 入口。更新暂存会复制见证程序；`npm run ha:witness -- <config.json>`、初始化和只读预检都从当前活动版本启动，回滚后随同切换。见证启动器保留命令参数和调用目录，因此相对配置路径及状态文件路径不会因版本目录改变。文件被改写、删除或增加时拒绝启动；见证程序不会因校验失败自动运行旧代码。

新版更新工具仍可校验、暂存、启用和回滚第 1 版清单的历史运行包，但第 1 版清单未覆盖的见证程序不能通过新版见证入口运行。旧安装目录的更新工具若只识别第 1 版清单，应先用新版完整运行包安装流程升级；不能靠修改清单版本号跳过校验。

原安装目录中的 `.data`、`.tools` 和 `.vendor` 不随应用版本切换。候选版本必须使用相同的固定 QEMU/PosixLoom 运行时；改变其版本时需走完整安装和数据迁移流程。上述历史 CLI 流程只校验文件完整性，不认证发布者。回滚恢复应用代码，不倒转新版本已写入的数据或外部存储。

## 可信更新中心

设置中的“可信更新中心”面向本地发行包。所有者先登记 Ed25519 公钥和声明来源，再输入包目录。检查通过后可暂存、查看候选版本、切换启动指针或回退。界面明确区分已认证发布者与未认证的历史版本。

包必须附带 `sakura-release-signature.json`。签名绑定发布者公钥指纹、来源、版本、发行指纹、递增序号和有效期。它认证包的发布者及声明来源；首版不从来源 URL 下载文件，也不实现完整 TUF 更新协议。

暂存前验证发布者信任、签名、有效期、序号和完整性。复制完成后再次验证副本，随后才安装依赖并运行隔离健康检查。相同序号或版本对应不同内容时拒绝；精确重复的已验证候选可复用。启用前重新检查发布者、有效期、发行指纹和健康记录。撤销公钥后，旧候选也不能启用。

信任配置保存在原安装目录的 `.sakura-update/trusted-publishers.json`。修改携带配置版本，跨进程锁防止并发覆盖。暂存取消由宿主进程监督器终止该次进程树；异常终止可能保留未完成候选或 `trusted-update.lock`。这类候选无法启用。确认更新进程已结束后，可人工检查并移除锁文件，再重新检查发行包。

回退界面展示目标版本。未认证的历史版本需明确勾选确认；版本目录仍须通过完整性校验。启动指针切换后，当前服务继续运行，重启后才使用目标版本。

## 发布者签名

发布者在发行清单生成后运行以下命令。私钥应保存在发行目录之外，脚本只向包写入签名文件。

```powershell
node scripts/sign-release.mjs D:\release\sakura D:\keys\release-private.pem https://example.org/releases 42 2027-01-01T00:00:00Z
```

每次发行使用递增序号，同一版本的内容指纹保持不变。把对应 Ed25519 公钥和来源交给使用者，并由使用者在界面登记。来源按 URL 的规范形式匹配，例如域名根路径包含结尾 `/`。签名文件已存在时，脚本拒绝覆盖。
