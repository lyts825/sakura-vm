# 第五批十个完整插件包设计

## 1. 版本、范围与交付标准

设计系列 **4.0.0 → 5.0.0**，日期 2026-10-25。应用保持 **2.7.0 → 2.7.0**，读取基线为 `5726601`，宿主插件 API 为 5。本文面向产品维护者、领域实现者和验收人员，承接[第四批设计](plugin-pack-next-design.md)。

本批设计 10 个完整插件包，共 **127 个拟议插件**。设计系列沿用按批次递增的版本习惯；5.0.0 不表示应用升级，也不替换以前的包。当前基线声明 130 个插件和 19 个包，2.8.0 另有在途实施。本批不登记运行插件，不改变默认选择，不扩大在途版本范围。

每个包都有独立输入、领域对象、核心处理、结果判断、版本保存、交接和清理流程。插件按独立存储责任、服务及生命周期拆分，数量由功能决定。模板、示例或模拟报告不能代替执行型包的真实工具验收。

## 4. 插件契约与独立使用

沿用[插件设计契约](plugin-design-contract.md)和[包协议](plugin-protocol.md)。每份详情声明包内前缀。依赖表中的短名补上此前缀，`@id` 表示基线已有插件；`—` 表示没有依赖，`*` 表示该表此前的全部插件。星号只用于文档，实施清单必须展开为精确 ID 和发行版本。

每个包的第一行插件唯一拥有工作空间根账本，其余插件直接依赖它。每行拥有独立领域对象和一个拟议公共服务。定义服务提供分页 list/get、带 expectedRevision 的 save、seal 和 archive；结果服务提供固定修订读取。所有存储者提供引用查询、清理预览和按原修订提交。

十个包互无必需依赖。网络、命令行、构建和桌面执行包需要既有 `projects`，其余包的离线流程无需启用其他业务包。可选适配器缺席时可以上传材料；提供者存在也不代表适配器已经实现。

来源适配器只交付固定副本、修订、适用范围及许可。接收端保留来源类别；上传相同字节仍为外来声明。首版跨包协作用显式导入，不自动订阅“最新”对象，也不把其他包的通过结论当成本包批准。

## 5. 完整产品的共同功能

每包均提供模板、准备检查、编辑器、完整计划预览、任务或计算进度、结果比较、审阅、封存、导入导出和清理入口。空状态说明下一步和缺项；错误保留草稿并提供原操作查询入口。页面须覆盖明暗主题、390 px 窄屏、键盘操作和锁定后私有数据清除。

| 功能 | 首版必须具备的行为 |
| --- | --- |
| 安装和选择 | 显示成员与精确依赖；默认不启用；遵守现有重启生效语义 |
| 输入和编辑 | 字段校验、固定来源、修订冲突比较、模板创建草稿 |
| 计划和执行 | 展示全部目标、输入、资源、输出和截止；分页不缩小批准范围 |
| 结果和比较 | 分开显示执行状态、业务结论、覆盖范围和资源清理 |
| 保存和恢复 | 封存版本不可覆盖；中断查询原意图及回执，不重放未知动作 |
| 交接和升级 | 导入隔离、完整校验、显式接受、模式迁移预览和来源映射 |
| 停用和清理 | 停准入并核销原资源；保留正式数据，按保护引用生成清理计划 |

共同对象保存 workspaceId、id、revision、schemaVersion、contentDigest 和 createdAt。服务端绑定真实 actor 和插件 generation。模板中的负责人、标注者和复核人只是业务字段，不产生新账号或权限。

定义采用 `draft → sealed → archived`。任务采用 `queued → preparing → running → finalizing → completed`，另有 failed、cancelled 和 interrupted。结论为 passed、failed、inconclusive 或 not-supported；清理为 pending、confirmed 或 unknown。处理完成不等于验证通过。

升级先检查对象模式及活动资源，再保存可恢复副本并预览迁移。新模式只在全部校验通过后提交；失败保留原版本和原字节。旧运行回执不能因升级重放。停用期间仍有未知资源时保留原实现及核销入口；降级不支持新模式时明确拒绝，不能删除字段后强行读取。

## 6. 页面、HTTP 与 CLI

详情中的服务、方法、路径及 CLI 都是拟议接口。命名方法使用 `POST /api/<完整插件ID>/<方法>`，逐路由声明严格请求、响应和操作策略；只读查询也须鉴权。禁止任意服务名、方法名或宿主命令分发。上传、下载与大正文读取使用独立的有界二进制路径。

CLI 前缀为 `sakura <包别名>`，支持 JSON 输出、分页、固定版本读取、preview、提交、status、wait、cancel 和 reconcile。退出码继承第四批：0 为当前命令完成，1 为已知业务失败，2 为输入或传输错误，3 为不确定或不支持，4 为清理待确认。多个情况同时存在时按 2、4、3、1、0 的优先级报告，并保留明细；异步提交的 0 仅表示接收。

离线 `verify` 不启动宿主、不联网、不执行导入内容，必须在纯 Node 安装产物中可用。它检查字节、结构及声明的可重算部分；原工具执行、来源认证与业务审阅分别报告。不能让 verify 重新运行导入脚本来“核验”报告。

计划固定目标、输入、工具、权限修订、资源上限和绝对截止，默认 5 分钟内有效。批准只消费一次，重复提交返回原回执；输入、身份或作用域改变后失效。已有有效授权不重复确认。

## 8. 容量、交换与恢复

每包数值均为拟定上限，须经实施验证；准入取对象、空间、包和宿主共同额度中最严格者。[现有共同容量](suite-capacity.md)默认 8 GiB，仅覆盖已登记范围；本批和新增 VM 预留均须接入，文档数值不修改实际配置。VM 按声明的虚拟磁盘容量预留，同时显示实际占用。

每包控制账本预留 32 MiB，包含在包总额中；普通写入不可消耗恢复保留。默认控制 JSON 1 MiB、上传块 512 KiB、读租约最长 15 分钟。原始/派生字节、索引、导入隔离、导出暂存和未知资源全部计费。共享字节只能由唯一存储者去重，不能忽略逻辑引用及删除保护。

普通交接采用 `sakura-<包ID>/1` 的 ZIP STORE 封套，继承[第三批有界格式](plugin-pack-suite-design.md)。拒绝压缩、ZIP64、路径穿越、符号链接、重复路径和大小写碰撞。清单固定长度、摘要和对象关系；离线分发的大载荷采用详情定义的显式分卷，不把普通封套无限扩容。

导入依次完成限额、结构、摘要、引用及业务规则检查，隔离审阅后接受到新空间。旧 ID 映射为新 ID，旧批准、秘密引用、运行票据和本地路径不生效。保留外来来源声明；摘要正确不等于来源认证。未配置并验证签名时明确为未认证。

跨插件提交先保存意图，分配有界暂存，再由各所有者发布，完成对象图后开放读取。中断只能核对原意图，不能凭缓存猜测成功。清理前复核原修订、撤权、活动读取和历史保护引用；停用或归档不自动删除材料。
